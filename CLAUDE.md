# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

- Before making any updates, cut a new branch from an up-to-date `stage` (`git checkout stage && git pull && git checkout -b <type>/<short-name>`). Never commit directly to `stage` or `main`; PRs target `stage`.

- when working on a 'feature' from the `_features.md` list, check off the tasks as you complete them.
- After adding or changing a feature, run a quick browser smoke test before calling it done: open it on the local stack (`npm run dev:local`, sign in with the matching test account), click through its buttons, menus, dialogs and forms, and read the browser console and failed network requests. Fix any warning or error the app causes; name any that come from outside the app (browser extensions, an expired session) instead of chasing them. Headless Playwright is fine when the MCP browsers are busy.
- Run the ui-ux-reviewer only after major UI changes (layout changes, new components or pages), not after every sprint of updates

## Commands

```bash
npm run dev          # Start dev server (http://localhost:3000) against .env.local (the hosted project)
npm run dev:local    # Local testing: starts the local Supabase stack, seeds test accounts, serves http://localhost:3100
npm run dev:seed     # Re-seed the local test accounts and "Test Table" (`-- --reset` rebuilds the hero's sheet)
npm run build        # Production build (nuxt build)
npm run generate     # Static site generation (nuxt generate)
npm run type-check   # TypeScript check (nuxt typecheck)
npm run lint         # Run oxlint then eslint sequentially, both with --fix
npm run format       # Prettier format all files
npm run test         # Vitest: utils, Nimble data integrity, golden level tables
npm run preview      # Preview production build locally
```

> Requires Node.js `^20.19.0 || >=22.12.0`. Use `nvm use 22.18.0` if needed.

## Stack

"Lantern": Vue 3 + Nuxt 3 (SPA mode, `ssr: false`) + TypeScript + Pinia + Supabase (auth, Postgres, storage, realtime). No UI library: custom components styled with SCSS and CSS variables. Hosted on Vercel.

## Design

`design/` is the reference (not wired into the app): `README.md` lists every screen, `screens/*.dc.html` hold exact markup and interaction logic, `tokens.json` the theme values. Match it when changing UI.

## Data model

Schema lives in `supabase/migrations/`; every table has RLS. Key points:

- `profiles` (public bits, role, theme, dice colour, `own_dice`) and `user_permissions` (flags, suspension, restriction reason) are separate so other players can't read someone's restrictions. Role and flags change only through `staff_*` / `admin_*` RPCs, which also write `moderation_history`.
- `characters.sheet` is JSON typed per system (`types/sheets.ts`); a trigger caps characters at 5 per user. Shared keys (`class`, `lineage`, `hp`, `hpMax`, `ac`, `initMod`, `passivePerception`) feed the `campaign_roster` RPC.
- A character joins a campaign through `campaign_members.character_id`.
- `messages.recipient_ids` null = whole party; otherwise a secret message to those users. `messages.kind` is `'chat'` (typed) or `'action'` (rolls and casts the battle board posts; the chat shows them as a compact log row only when the viewer turns on "Battle log" (off by default, remembered per browser); they raise no notifications and the dashboard skips them).
- NPCs: `npcs` is the shared pool (official + approved homebrew); only staff write it. Players suggest entries through `npc_submissions` (pending → approved/rejected via the `staff_approve_npc_submission` / `staff_reject_npc_submission` RPCs). `campaign_npcs` are a campaign's own copies and never reach the pool on their own.
- Policy helpers live in the `private` schema (`is_staff`, `can`, `is_campaign_member`, `is_campaign_gm`).
- `hero_effects`: a status one hero gives another (Help → "Helped"). Sheets don't reload while open, so the helper never writes the target's sheet: `composables/useHelpAlly.ts` inserts the row, and the target's own sheet or board panel (`useHeroEffects`) adds the status and deletes it, live or on next load. Members insert for heroes seated in their campaign; only the target's owner reads and deletes.
- Battle board: `combatants.conditions`, `actions_max` and `actions_used` hold a combatant's conditions and action pips; `campaign_initiative()` gives players the conditions but null action counts. `campaign_hero_card` is a members-only RPC returning a hero's public subset for the stats dialog, with `system` and that system's keys (5e `abilities` are the six scores plus `features`, PF2e `skills` carry rank and value plus `feats`; Nimble's keys stay for every system; numbers are read with `private.jnum`, so a cleared field ("") falls back to a default instead of failing the cast); `campaign_roster`'s summary also carries `abilityNames` (for `turnActionsFor`) and PF2e `heroPoints`, `focus` (`current` / `max`) and `wounded`.
- `hero_hp_changes`: an HP change the GM makes to a hero (mirrors `hero_effects`). The GM inserts through `useSendHeroHp`; only the owner reads and deletes. The hero's own sheet or board (`useHeroHpChanges`, every system) applies it with that system's rules (`applyHpChangeFor`: Nimble `takeDamage` / heal; 5e temp HP first, damage at 0 fails a death save (2 on a crit), damage past 0 that reaches max HP kills (massive damage), healing from 0 resets the death saves; PF2e temp HP first, 0 HP sets Dying 1 + Wounded (2 on a crit), more damage at 0 adds 1 Dying (2 on a crit, up to 4), healing a dying hero ends Dying and adds 1 Wounded) and claims it by deleting the row first, so it applies once; `utils/heroHpChange.ts`, `tests/heroHpChange.test.ts`
- `hero_condition_changes`: a condition the GM adds to or removes from a hero (stats modal, `useSendHeroCondition`). The `gm_set_hero_condition` RPC writes the saved sheet at once for every system (so it holds while the player is away; 5e and PF2e a plain add or remove, no end) and leaves the row for an open sheet, which `useHeroConditionChanges` applies live (`applyConditionChangeFor`: Nimble `addCondition` / `removeCondition`, else a plain add or remove; a no-op when it matches; only the last change per condition); `utils/heroConditionChange.ts`, `tests/heroConditionChange.test.ts`
- Initiative (`encounters`, `combatants`) is GM-only; a player moves only their own seated hero and its summons with `set_my_initiative` (security definer). `encounters.initiative_mode` is the campaign's rules (a GM toggle in the battle board's ⋯ menu, shown for Nimble campaigns only; other systems are always `classic`): `nimble` puts heroes first and lets the roll set their starting actions, `classic` orders by the roll and starts heroes with full actions (`useCampaignEncounter` → `sheet.classicInitiative`, read by `initiativeRoll`); `sortOrder(rows, mode)` applies it. Add party seats heroes with `initiative_rolled = false` ("–", top of the order) until `set_my_initiative` or the GM sets it. `useCampaignEncounter` also tells every sheet editor whether its hero is seated: being seated runs New encounter on the sheet (it then asks for Initiative), leaving the tracker runs End encounter (`seatChange` in `utils/turnSteps.ts`), and while seated (`editor.gmEncounter`) the player's steps are only Roll Initiative, Start turn and End turn.
- Lore Master context is chosen in the Edge Function from the caller's `campaign_members.role`: a GM gets the campaign (roster, sheets, NPCs, journal); a player gets only their own character, so campaign secrets never reach a player's prompt.
- Free Lore Master allowance: `ai_free_usage` (one row per user per UTC day, users read their own). Only the service role calls `use_free_ai` (atomic take, returns questions left or -1) and `refund_free_ai` (when the provider call fails); admins set the cap with `admin_set_free_ai_limit`.
- `analytics_events`: usage events (view / click / time) per user, surface, seat and viewport. RLS on with no policies: clients insert only through `track_events` (at most 300 events per user per minute; no-op while `site_settings.analytics_enabled` is off, the "Usage analytics" switch in Site features), staff read totals only through `staff_analytics_surfaces` / `_splits` / `_daily` / `_buttons` (staff accounts excluded unless asked); `staff_analytics_prune` drops events older than 180 days when the page opens; admins can wipe everything with Reset analytics (`admin_reset_analytics`, confirmed in a dialog, logged to `moderation_history`).
- Storage buckets: `portraits` (public), `campaign-files` (`{campaign_id}/…`, members only), `library` (`{user_id}/…`, any signed-in user can read).

## Linting

Dual linter setup — both must pass:

1. **Oxlint** (Rust-based, fast) — runs first, covers correctness rules
2. **ESLint** (flat config in `eslint.config.ts`) — runs second with caching
